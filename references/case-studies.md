# docx-helper 实战案例库（踩坑经验）

> 本文档沉淀自 2026-08 宿迁市公共数据平台系列文档（保密协议/开放管理规范/应急预案/重保方案/巡检规范）处理中遇到的真实问题与解法。处理同类文档时先读这里。

## 案例 1：图文错位（浮动图片衬于文字下方）

**症状**：正文文字从图片上直接穿过，图文重叠。常见于"组织架构图""流程图"。

**根因**：原文档图片是**浮动定位**（`<wp:anchor>`），且设置了 `behindDoc="1"`（衬于文字下方）+ `wrapThrough`（穿越环绕）。浮动图片不占段落位置，文字自然从其上穿过。

**排查法**（解包 docx）：
```python
import zipfile, re
xml = zipfile.ZipFile(f).read('word/document.xml').decode('utf-8')
print(re.findall(r'<wp:anchor', xml))  # 浮动图片数
print(re.findall(r'<wp:inline', xml))  # 嵌入图片数
```

**解法**：浮动 anchor → 嵌入 inline（图片独立成行、段落居中，文字自动避让）。已内置 `--fix-images` 命令，`--apply` 排版时也会自动执行。

**注意**：不要试图用"减小图片尺寸"或"调整环绕方式"绕行——浮动定位本身就是错的，必须转嵌入。

## 案例 2：落款行（日期/签名）对齐

**症状**：巡检日期/巡检人两行的「巡」字不对齐；或落款位置反复返工（右对齐→居中→左对齐…）。

**根因与结论**：
1. **位置**：落款应在正文**右下角**（GB/T 9704-2012 §7.3.5 成文日期右空四字），用户直觉是对的。
2. **对齐**：多行落款（日期行 + 签名行）首字要对齐，**不要用"等宽右对齐"**——右对齐时半角空格实际渲染宽度依赖字体度量，算得等宽、渲染不等宽，首字必错位。
3. **可靠方案**：两行都设**左对齐 + 相同左缩进**（`left=3700 twips` ≈ 右空四字位置），首字从同一 x 坐标开始，天然竖直对齐，与内容宽度无关。
4. **签名留白**：签名行末尾用**半角空格**（约 16 个）留出签名位，不要删掉——那是手写签名区。

**实现**：已内置 `signature` 类型（左对齐 + 左缩进 3700 twips）。

**常见返工路径**（避免重蹈）：右对齐→居中→左对齐+缩进→等宽右对齐→左对齐+左缩进。最终方案即最后一种。

## 案例 3：自动编号烘焙错误

**症状**：reset 后「一、二、三」中文序列变成「1、1、1」不递增，或「（一）（二）」变「（1）（1）」。

**根因**：Word 自动编号（`w:numPr`）在 reset 时被烘焙为正文文本，依赖 `_format_num` 对 `numFmt` 的支持：
- `japaneseCounting` / `chineseCounting` / `chineseLegalSimplified` 等中文格式必须映射到中文数字转换
- 同一列表内段落（numId 相同）不能被误判为新列表而重置计数——延续判断必须是"不小于即延续"（`_numid_ge`），不能用"大于"

**排查法**：处理新文档前先检查是否含自动编号：
```python
import zipfile, re
z = zipfile.ZipFile(f)
print('numbering.xml:', 'word/numbering.xml' in z.namelist())
print('numPr 段落数:', len(re.findall(r'<w:numPr>', z.read('word/document.xml').decode('utf-8'))))
```

**注意**：reset 后务必抽查编号文本是否递增正确（`--list` 查看）。

## 案例 4：注的编号对齐（注：1.… / 2.…）

**症状**：表格下方"注：1.×××；2.×××。"两行，1 和 2 对不齐。

**错误做法**（均不可靠）：
- 第 2 行用全角空格（\u3000）手凑对齐——空格宽度依赖字体
- 两行做两个独立段落、分别设缩进——段落间缩进叠加关系不可靠
- 混用 firstLine（绝对磅值）与 leftChars（字符单位）——单位机制不同

**可靠方案**：**单段落 + 软换行（w:br）+ 悬挂缩进**：
- 两行合并为一个段落，中间插 `<w:br/>`
- 段落设 `left=4字符 + firstLine=-2字符`（悬挂缩进，字符单位）
- 首行「注」在第 2 字符处，「1.」在第 4 字符处；续行「2.」由悬挂缩进**自动**定位在第 4 字符处——这是 Word 列表续行的原生机制，不依赖任何字符宽度估算

**python-docx 实现要点**：把第二段 runs 移到第一段（中间 append `w:br` 元素），删除第二段，设置 `ind`（left=1280/leftChars=400/firstLine=-640/firstLineChars=-200）。

## 案例 5：条款段内混排（第X条）

**场景**：法规条文「第一条　公共数据开放主体应当按照…」——条号前缀楷体、条款内容仿宋（用户明确要求）。

**实现**：整段样式覆盖不了，需拆 run：
```python
import re
from docx import Document
from docx.oxml.ns import qn
doc = Document(f)
for p in doc.paragraphs:
    if re.match(r'^第[一二三四五六七八九十百]+条', p.text.strip()):
        # 遍历 runs，把条号前缀所在 run 的 eastAsia 设为楷体，内容 run 设为仿宋
        for r in p.runs:
            rpr = r._element.get_or_add_rPr()
            rf = rpr.get_or_add_rFonts()
            is_prefix = re.match(r'^第[一二三四五六七八九十百]+条', r.text)
            rf.set(qn('w:eastAsia'), '方正楷体_GBK' if is_prefix else '方正仿宋_GBK')
```

**注意**：条号与内容之间的空格是原文分隔，保留；字号统一三号。

## 案例 6：正文条款被误判为标题

**症状**：「1. 巡检人员应于一天内完成当次巡检任务并填写巡检表…」这类**数字编号 + 长正文**被启发式判为 h3 标题（无缩进）。

**规则**：编号后剩余文字**超过 30 字符**视为正文条款 → 判 `body`（首行缩进 2 字符），而非标题。已内置到 `_classify`。

## 通用检查清单（每次处理完必查）

1. `--check-content`：错别字/叠词/编号异常（一但→一旦、防范未然→防患未然、日常日常→日常、任意任意→任意；重号/跳号/顺序错乱，支持（1）/1./一、 三种格式）
2. 页码：奇数右下、偶数左下，四号 — N —
3. 表格/图片数量不丢失（解包对比原文档）
4. 页面设置：上3.7/下3.5/左右2.7cm、页脚距2.54cm
5. 行距全文统一 28.9 磅固定
6. 落款行：左对齐 + 左缩进 3700 twips，首字对齐，签名留白
7. **AI 过程复核（通读成品）**：结构误判（落款排成正文/图题未居中）、内容误伤（编号烘焙/特殊字符丢失）、位置异常（图片嵌入/落款位置）、关键观感（标题孤悬页尾/封面分页）——规则执行正确 ≠ 结果合理
8. **用户最终验收（必做）**：AI 复核看不到 Word 渲染效果（孤行/孤页/图片叠压），且复核的是自己判定的结构（有确认偏误）——交付时给"重点确认清单"，**最终视觉验收由用户在 Word 中打开确认**（本技能落款曾返工 7 版，最终靠用户看截图纠正）
